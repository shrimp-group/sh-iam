# STORY-048 — 权限信息缓存与权限判断

> 状态：✅ 已完成 ｜ 优先级：P0 ｜ 模块：iam-session + iam-portal + iam-admin ｜ 完成日期：2026-11-02 ｜ 扩展：2026-11-03（super 用户与公共角色，见 §7）
> 权威设计记录：本文档 + `AuthCacheManager` 类 javadoc（权威状态映射表）

## 1. 背景与目标

权限判断原为每次请求直查 DB（或返回应用全量菜单、无用户过滤），高频接口下数据库压力大且语义不精确。本故事实现三级权限缓存与权限判断体系：

- 系统静态资源（角色/菜单/按钮/关系/接口/字段/限流配置）按应用一次加载，按需缓存
- 用户角色按用户缓存，低频菜单树每次计算不缓存，高频接口权限按 URL 缓存 true/false
- 权限变更（管理端操作）经事件 → Redis 通知全局清理；按需精确清理（APP_STATIC 联动 L3 整组，USER 精确到用户）
- 指令带时间戳去重，多实例/轮询/订阅并存幂等
- 支持 iam-session 独立部署（跨 Redis 场景）的远程取数与变更轮询

## 2. 方案摘要

### 2.1 三级缓存结构（Guava，AuthCacheManager + AuthComputedCache）

| 层 | 类型          | 键                      | 内容                                                                                                                                   | 加载                                                      | 失效                                                                                   |
|----|---------------|-------------------------|----------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------------|----------------------------------------------------------------------------------------|
| L1 | APP_STATIC    | appCode                 | `AppAuthResource`（app=AuthApp（appCode/appName/authType）/roleCodes/**publicRoleCodes**/menuMap/roleMenuMap/apiMap/menuApiMap/requestControls/apiFields） | 首次访问按需，facade.loadAppResource 一次加载一个应用全量 | APP_STATIC 指令精确清理 + 容量 LRU；本地形态无 TTL，远程形态 expireAfterWrite TTL 硬界 |
| L2 | USER_ROLE     | userCode                | `List<String>` 有效角色（super 用户为哨兵 `__SUPER__`，见 §7）                          | 首次触发该用户权限计算，facade.loadUserRoleCodes          | USER 指令 / 会话终结 + 空闲 TTL（expireAfterAccess）+ 容量 LRU                         |
| L3 | USER_COMPUTED | appCode→userCode→urlKey | `Boolean`（METHOD:URI → true/false）                                                                                                   | 首次判断该 URL 按需单点计算（未命中才计算，不预计算全量） | URL 级 TTL（expireAfterWrite）+ 用户级空闲 TTL + 指令/会话终结联动清理 + 容量 LRU      |

**用户缓存生命周期**：空闲 TTL（`user-idle-seconds`，默认 30min）覆盖「久不活跃」；退出登录/登录超时/被踢出由
`AuthCacheSessionCleaner` 监听 SessionEvent（DESTROYED/EXPIRED），剩余会话为 0 时 `evictUser(SESSION_END)`；多端登录仍有剩余会话则保留。

**快照不可变约束**：L1 内 `AppAuthResource`（menuMap/roleMenuMap/apiMap/menuApiMap
等）为多请求共享实例，任何计算不得修改其字段——组树必须浅拷贝节点，严禁对缓存内实例 setChildren（否则并发请求互相污染树结构）。

### 2.2 联动清理映射

| 指令类型            | 清理范围                             | 理由                                 |
|---------------------|--------------------------------------|--------------------------------------|
| APP_STATIC(appCode) | L1[appCode] + L3 整组[appCode]       | 动态计算结果受静态资源影响，一同清理 |
| USER(userCode)      | L2[userCode] + L3 各应用内[userCode] | 精确到用户，不波及他人               |

### 2.3 状态映射（权威定义见 AuthCacheManager 类文档）

- **条目状态流转**：`NOT_LOADED →(ON_DEMAND) LOADED →(CHANGE_CMD | SESSION_END | TTL | LRU) EVICTED(=NOT_LOADED)`，条目状态由
  Guava 存在性编码；统一 `[auth-cache]` 日志前缀（type/key/from→to/reason）
- **指令流转**：`PUBLISHED → RECEIVED → APPLIED | IGNORED_STALE`。去重规则：`lastAppliedTs`（ConcurrentHashMap，key=type:
  targetKey）记录最后已处理时间戳，仅处理更新的指令，重复/乱序旧指令忽略（逐出幂等，重复无害）；订阅与轮询共用 `applyCommand`
  入口

### 2.4 跨 Redis 三层防线（iam-session 独立部署场景）

宿主应用与 portal 可能使用不同 Redis 套餐，Pub/Sub 不可达：

1. **轮询同步（主通道）**：`AuthChangePoller`（配置 server-url + `poll-interval-seconds>0`）定时调 portal
   `/public/auth/changes` 拉取变更日志 Hash（每键最新指令）→ 逐条 applyCommand；拉取失败吞并等待下轮
2. **L3 URL 级 TTL**（`computed-ttl-seconds`，默认 300s）：判断偏差硬界
3. **远程形态 L1 TTL**（`static-remote-ttl-seconds`，默认 300s）：静态数据陈旧性硬界（本地形态无 TTL）

发布端双写：Pub/Sub channel + 变更日志 Hash（`iam:auth:change-log`，field=type:targetKey 同键覆盖，TTL 7 天）。

### 2.5 鉴权基准与鉴权类型（ownerKey，§7.4 重构）

AuthPermissionFilter 判定基准为**服务归属资源键 ownerKey**，与调用方 header appCode 无关（跨应用调用安全）：

- **独立部署**（配置 `iam.session.app-code`）：ownerKey = 配置值，鉴权深度按应用 `iam_app.auth_type`（经 `AuthApp.app` 随 L1 加载）
- **合并部署**（未配置）：ownerKey = `__GLOBAL__`（AuthCacheManager.GLOBAL_KEY），L1 资源打平（9 条 SsoAuthResourceMapper 查询 app_code 条件动态化，全量聚合），鉴权深度按全局配置 `iam.auth.auth-type`（替代原 `iam.auth.check.enabled` 开关）

鉴权类型语义（判断入口 `AuthPermissionService.requireApiPermission(ownerKey)`）：

- **TOKEN**：仅需会话认证（SessionAuthFilter），AuthPermissionFilter 跳过纳管与接口权限校验
- **TOKEN_API**：会话认证 + 全量纳管 + 接口权限校验
- **空值/未知值**：安全默认 TOKEN_API（fail-closed，解析见 `AppAuthType.of`）

header appCode 仅业务层使用（菜单树计算按调用方应用）。APP_STATIC 指令清理时联动清理 L1[`__GLOBAL__`]（打平资源受任意应用变更影响）。"仅登录"差异化接口（合并部署）→ 注册 API 授权给公共角色（is_public=1）。设计全文：`docs/design/uri-owner-auth-design.md`。

### 2.6 有效角色规则（§7 扩展）

`AuthPermissionService.collectBoundMenuCodes` 计算有效角色：

- **super 用户**：L2 仅含哨兵 `AuthResourceFacade.SUPER_ROLE_CODE`（`__SUPER__`）→ 应用内全部角色的菜单并集（未绑角色的按钮/菜单仍不可见）
- **普通用户**：绑定角色（iam_user_role，L2）∪ 应用公共角色（`is_public=1`，随 L1 publicRoleCodes）→ 与应用角色取交集合并菜单
- 公共角色变更走既有 APP_STATIC 指令（IamRoleService 发布）；super 哨兵随 L2 生命周期（USER 指令/空闲 TTL）

## 6. 常见问题排查

- **缓存不更新**：查 `[auth-cache]` 日志——`APPLIED` 表示指令已应用；`IGNORED_STALE`
  表示指令时间戳不新于已处理（去重生效，非故障）；均无则检查管理端操作所在事务是否提交（AFTER_COMMIT 才发布）与 Redis
  channel/轮询配置
- **权限判断偏差**：L3 URL 级 TTL 内为已知偏差窗口；变更指令到达即清；跨 Redis 场景确认 `poll-interval-seconds` 已配置
- **远程取数 401**：核对两端 token 配置一致（`iam.portal.auth.token` vs `iam.session.remote.auth-token`）

## 7. 扩展：super 用户与公共角色（2026-11-03）

### 7.1 super 用户（配置化）

- **定义**：portal 配置 `iam.portal.super-users`（userCode 逗号分隔，默认 `root`），无表结构变更
- **机制**：`LocalAuthResourceFacade.loadUserRoleCodes` 命中配置（trim 后精确匹配）→ 返回哨兵
  `AuthResourceFacade.SUPER_ROLE_CODE`（`__SUPER__`），不查 iam_user_role；哨兵随 L2 缓存，
  权限计算侧视为拥有应用内全部角色（全部角色菜单并集，见 §2.6）
- **防误判**：哨兵码占用角色编码命名空间——`loadUserRoleCodes` 出口剔除与哨兵同名的真实角色编码，
  super 语义只来源于配置判断，DB 撞名角色无法触发提权
- **边界**：未绑定任何角色的菜单/按钮 super 用户亦不可见（语义=拥有所有角色，非绕过角色模型）；配置变更需重启生效

### 7.2 公共角色（iam_role.is_public）

- **DDL**：

```sql
ALTER TABLE iam_role ADD COLUMN is_public TINYINT NOT NULL DEFAULT 0 COMMENT '是否公共角色：1-是，0-否' AFTER applicable;
```

- **链路**：`listAppPublicRoleCodes`（is_public=1）→ L1 `publicRoleCodes` → 有效角色 = 绑定 ∪ 公共（§2.6）
- **语义**：公共角色无需申请/绑定，用户访问应用即自动拥有该角色下全部功能；无需 iam_user_role 数据与授权流程
- **缓存**：公共角色属 L1 应用静态资源，角色 create/update/remove 既有 APP_STATIC 指令自动清理，无新增清理逻辑
- **管理端**：IamRole.isPublic（copy 同步）；角色列表/树/编辑/详情展示与编辑（iam-admin-ui）

### 7.4 扩展：鉴权基准重构（2026-11-04，设计文档 `docs/design/uri-owner-auth-design.md`）

跨应用调用下鉴权深度被按调用方 appCode 判定（根因：appCode 仅隔离菜单、未做部署隔离）→ 鉴权基准改为**部署形态分流**：

- **独立部署**：`iam.session.app-code` 配置归属应用 → 现状按应用 L1 + 应用 auth_type
- **合并部署**：不配置 → L1 打平为 `__GLOBAL__`（SsoAuthResourceMapper 9 条查询 app_code 动态化），鉴权深度按全局 `iam.auth.auth-type`（替代 `iam.auth.check.enabled` 开关）；权限=用户全部角色授权链并集（安全性论证见设计文档 §2.1）；"仅登录"差异化接口 → 注册 API 授权公共角色
- **filter 判定链**：删全局开关步与 header appCode 强制校验；ownerKey 分流（AuthCacheManager.GLOBAL_KEY）；APP_STATIC 指令联动清 GLOBAL L1/L3
- **API 全局唯一**：IamApiService.duplicateCheck 唯一条件升级 method+uri（跨应用）；导入路径 validateImport 增加 method+uri 校验（导入项间 + 库中 `listAllMethodUris` 批量比对）
- **兼容红线**：远程 iam-session 形态必须配置 app-code（否则 GLOBAL 远程取数返回空资源 → 已登录请求全 403）；RequestControlFilter 仍按 header appCode 匹配限流（本次范围外）
- 验证：全仓 `mvn -q clean test` exit 0（新增 AuthPermissionFilterTest 部署形态用例、AuthCacheManagerTest GLOBAL 联动、AuthPermissionServiceTest 全局 auth-type、LocalAuthResourceFacadeTest GLOBAL 打平）
